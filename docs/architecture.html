The sign-in chain

How a phone number ends up deciding which rows a person can see. Each step hands one thing to the next.

  1. PhoneFarmer picks the country code and types the mobile number. toE164() turns it into +919876543210.
  2. OTPsignInWithOtp({ phone }) asks Supabase to send an SMS code; verifyOtp({ phone, token, type: 'sms' }) checks it. Resend waits 60 s.
  3. Supabase AuthCreates the account on the first verified sign-in and returns a session. The login token (JWT) carries the user id as sub. The session is saved on the phone, so the app opens offline.
  4. user_idAuthProvider reads session.user.id. The same number always maps to the same id, on every phone.
  5. localStoragestorageService.setScope("u:<user_id>:"): each person on a shared phone has a separate area.
  6. syncsyncService uploads new, edited and deleted records under that user_id and downloads changes from other phones.
  7. tracker_itemsOne row per worker, work day or payment: user_id, collection, id, data, deleted, updated_at.
  8. RLSFour policies allow SELECT, INSERT, UPDATE and DELETE only where user_id = auth.uid(), the id inside the login token. Tested on the real database by tests/rls/tracker_items_rls.sql.

4

Phone OTP login and per-user data

Built

People sign in with their mobile number and a code sent by SMS through Supabase Auth. The first verified sign-in creates the account. After sign-in, storage switches to that user's own area on the phone, so two people sharing a phone never see each other's data. Data saved before accounts existed moves to the first person who signs in.

  • auth/phone.tsNumber clean-up to +91… form, 6 to 10 digit code check, error messages
  • auth/AuthProvider.tsxShows login until signed in, then scopes storage and starts sync

5

Cloud sync backend

Built

Every save goes to the phone first, then uploads in the background. Other phones download changes when they open the app, come back online, or after a save. If two phones edit the same record, the later edit wins.

Frontend (sync engine)

  • services/syncService.tsPush: compares records with what was last uploaded and sends only new, edited or deleted ones
  • Pull: fetches rows changed since the last pull, 1,000 at a time, and merges by updatedAt
  • Triggers: 0.8 s after a save, when back online, when the app becomes visible

Backend (Supabase Postgres)

  • tracker_itemsOne row per worker, work record or payment: user_id, collection, id, data, deleted, updated_at
  • Row-level security4 rules: a user can only read, add, edit or delete their own rows
  • Trigger tracker_items_touchThe server sets updated_at, so a phone with a wrong clock can't hide changes
Connects to phase 4: listens to storageService.onWrite, and writes downloaded data with { silent: true } so it isn't uploaded again. Connects to phase 2: when a pull changes data, AuthProvider remounts the screens so the dashboard shows it.

How data moves

Saving a work day

  1. WorkEntryForm calls workService.create()
  2. Validation and wage calculation in domain/
  3. storageService.write() saves to the user's area in localStorage
  4. The write event schedules a sync 0.8 s later
  5. syncService upserts the new row into tracker_items

Opening on a second phone

  1. AuthProvider restores the saved login
  2. Storage switches to that user's area
  3. Pull asks for rows newer than the last pull
  4. mergeRows() keeps the newer edit and applies deletions
  5. Screens remount and show the merged data

Exporting

  1. Tap Export Excel or Export PDF
  2. buildExportTables() or buildStatement() prepares rows
  3. The Excel or PDF library loads on first use
  4. The file downloads straight on the phone

  A->>L: Save
  Note over A,D: Back online, the next sync uploads it
